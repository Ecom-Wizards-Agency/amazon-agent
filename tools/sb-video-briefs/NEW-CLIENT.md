# New client setup: SB video briefs

1. Copy `config.TEMPLATE.json` to a local gitignored config per client, marketplace and product line. Set `briefing.mode` to `production` or `concept_testing` and `briefing.requested_cuts` to the number of complete scripted cuts before language/export duplicates.
2. Fill the client, language, current ASIN/pack, factual basis, brand kit and existing client Video Briefings folder. Concept testing also requires the exact Seller Central account-picker name, expected partnerAccountId, optional agency parent and marketplace label. Production document preparation with supplied evidence may omit Seller Central identity; any actual Amazon collector still verifies its account before access. These inputs do not authorize an Amazon or client-visible write.
3. For concept discovery, pin the authoritative keyword workbook and record the SoldScope run, SYNQ client and POE coverage. Confirm one cluster from the shortlist before scripting. An already agreed production objective uses supplied verified evidence without repeating this research/approval ceremony.
4. Keep research and claims provenance internal under `references/creative-reference-doc.md`. Supply verified useful footage links when available; otherwise describe the intended result without assuming source clips. Record known required-shot gaps precisely.
5. Write one complete briefing using the editor template. Production has one Video section per requested cut; concept testing has three openings and one shared Part 2 per confirmed concept. Voiceover, duration and branded intent follow the specific assignment.
6. Run the portable validator: `python3 -I -B <skill-root>/scripts/validate_brief.py --brief-md <file> --mode production --requested-cuts 1`. Use `concept_testing` and the appropriate cut count for test jobs. Resolve independent factual/creative review findings.
7. After authorization for client-visible delivery, run `python3 tools/sb-video-briefs/build_and_deliver.py --config <config> --brief-md <file>`. It creates one branded native Google Doc or updates the configured `delivery.brief_document_id` in place. Verify title, folder, native MIME type, full content readback, PDF export and every page's visual layout before declaring delivery complete.

Legacy configs without `briefing` retain concept-testing validation. Legacy `client.amazon_account`, break-even, `testing`, reference title/ID and `--reference-md` values are ignored with warnings. Historical reference Docs are never created, edited or deleted. A brief ID no longer needs a reference ID. The delivery manifest says `delivered_pending_visual_qa` until the attending workflow finishes page inspection.

An OpenBot skill copy contains the portable validator, not the repository's authenticated delivery dependencies. Prepare the brief and checks locally, then use the supported delivery handoff if that capability is unavailable. Do not call local files a delivered briefing.
