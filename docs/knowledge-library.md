# Amazon knowledge library

`knowledge/` is the authored library of Amazon answers the team's agents search first for a symptom, an error text or a "how do we handle X" question. It holds what the agency learned on real accounts, anonymised, one unit per question, each labelled with how far it has been verified. It sits beside the captured libraries (`Amazon Seller Help`, `Amazon Ads Help`, `Advertising Help After Login`, `MAG SOPs`) and is searched through the same helper, so Grimoire in Slack and every local session reach it without new tooling.

## The rule: repo or vault?

Strip every client-specific token from the lesson: brand, product, person, ID, amount, link, date finer than month. If what remains still teaches any teammate how to recognise and solve the problem on any account, it is a knowledge unit here (public, anonymised, labelled verified or unverified). If what remains is empty or meaningless without the client, it belongs in the team vault: `Clients/{Name}/Runs/`, `Amazon Ops.md`, or a one-line Lesson.

One fact has one home. The repo holds the rule; the vault holds the evidence and the provenance (who, where, the Slack permalink, the case or shipment IDs), joined by the unit ID. First-party captures and MAG SOPs stay captures and are never hand-edited. Skills stay procedure; a unit links a skill's steps instead of restating them. People appear as roles only in the repo (the client, the SAS manager, a Seller Support associate); the vault ledger records teammates as Slack IDs or roles and never records a client contact's name. An attended triage may delete an SOP the agency cannot use (a platform it does not sell on, a tool it does not run) and rebuild the SOP index; a stale but relevant SOP is superseded by a unit or a skill reference and marked in the index, never rewritten.

## Layout

```
knowledge/
  README.md                       generated: counts and unit list per topic
  TEMPLATE.md                     the unit skeleton
  _index/knowledge-index.json     generated by tools/knowledge/build_knowledge_index.py
  compliance/ logistics/ catalog/ support-cases/ ads/ account-health/ seo/ brand-registry/ reporting/
  _retired/                       retired units, excluded from search
```

Topic folders map to owning skills: compliance (`amazon-regulated-product-appeals`, `amazon-seo` claims), logistics (`amazon-logistics`, `amazon-fba-inventory-planning`), catalog (`amazon-catalog`, `amazon-flatfilepro`), support-cases (`amazon-communications`), ads (`amazon-ads-console`, `amazon-audit`, `amazon-ppc-weekly-management`), account-health (`amazon-account-health-check`), seo (`amazon-seo`), brand-registry (`amazon-catalog`), reporting (`amazon-reporting`). `amazon-troubleshooting` routes a symptom to the right topic.

## Unit format

File: `knowledge/<topic>/KC-NNNN_<slug>.md`. The id `KC-NNNN` is stable, zero-padded, assigned by `tools/knowledge/new_unit.py`, never reused (retired units keep theirs). The slug is lowercase kebab, symptom-first, no brand. Copy `knowledge/TEMPLATE.md`; the lint enforces the keys, their order, the enums and the section order.

Frontmatter is a flat YAML subset that the stdlib parser in `tools/knowledge/kb_frontmatter.py` reads: `key: value` lines only, values are a bare scalar, a double-quoted string, `true`/`false`, or an inline list `[a, "b c"]`. No nested maps, no multi-line values.

| Key | Values |
|---|---|
| `id` | `KC-NNNN`, equals the file name prefix |
| `title` | quoted, symptom first, no client token |
| `kind` | `diagnosis`, `procedure`, `rule`, `reference`, `decision-aid` |
| `topic` | the folder name |
| `status` | `draft` (not yet human-ticked), `reviewed` (ticked), `retired` |
| `skills` | list of skill names under `skills/` |
| `marketplaces` | list of `US`, `CA`, `MX`, `DE`, `UK`, `FR`, `IT`, `ES`, `NL`, `SE`, `PL`, `AU`, `JP`, or `[all]` |
| `marketplace_inferred` | `true` when the source did not state it |
| `surface` | quoted UI path or tool, `surface_verified` true once seen live |
| `symptom_keywords` | how people ask; the search helper boosts phrase hits |
| `error_text` | verbatim Amazon notices or codes; the search helper boosts exact hits |
| `resolution_status` | `resolved`, `partial`, `diagnosis-only`, `unknown` |
| `fix_source` | `agency`, `client`, `amazon-support`, `first-party-doc`, `unknown` |
| `evidence_location` | `slack`, `screenshot`, `call`, `email`, `case`, `video`, `run-note`, `none` |
| `confidence` | `high` (first-party rule or repeated confirmation), `medium`, `low` (single thread) |
| `verification` | `unverified` or `verified`; then `verified_on` `YYYY-MM-DD` and `verified_how` `live-ui`, `first-party-capture` or `operator` |
| `amazon_sources` | repo paths of local first-party captures; must exist |
| `related_sops` | repo paths of MAG SOPs or drafts that cover part of it; must exist |
| `supersedes` | repo paths this unit replaces (the SOP index marks them `superseded`) |
| `contradicts` | repo paths whose statement this unit contradicts; stays until a human resolves it |
| `observed` | `YYYY-MM` first seen; `review_by` `YYYY-MM`, default observed plus 12 months |
| `provenance` | `ledger:KC-NNNN`, the only pointer to the private ledger |

Body sections, in this order, all present: `## Question`, `## Answer`, `## Cause`, `## Fix`, `## Verify`, `## Stop before`, `## Sources`, `## Gaps`. Keep a unit under 90 lines; a long procedure goes to `sop-drafts/` and the unit links it. English only; dates `DD.MM.YYYY` in prose.

## Verification states

A unit enters as `status: draft`, `verification: unverified`. A human tick sets `status: reviewed`: the agency lead ticks any unit, the ads lead ticks ads units, and the operations lead ticks logistics, catalog, support-cases and account-health units from threads they owned. The agency lead decides every policy-risk or not-publishable card. A live read-only check in the attended browser, or a matching first-party capture, sets `verification: verified` with the date and method. Units whose `review_by` has passed, or whose cited help page changed after `verified_on`, are listed by `tools/knowledge/kb_status.py` and go back to review. An answer built on an unverified unit says so.

Authority order when sources disagree: the live Amazon page read on a named date, then the local first-party capture, then a live-verified skill, then a MAG SOP, then the Slack observation. Agents never resolve a conflict silently; the unit lists the other source in `contradicts`, and ads conflicts also go to the vault `Research/amazon-ads/challenges.md`.

## Privacy and the ledger

Nothing with a client name, product name, person's name, ASIN, SKU, FNSKU, EAN, shipment, case, order or removal ID, merchant token, price, unit count, address, 3PL or vendor name, Slack ID, Slack permalink, or Drive, Notion, Zoom or Cap link enters `knowledge/`. `tools/knowledge/scrub.py` holds the regex classes; the gitignored `_local/knowledge-redaction-terms.txt` holds the denylist (seeded by `tools/knowledge/seed_redaction_terms.py` from the vault client hubs and the Grimoire client list, then extended by hand). `tools/knowledge/lint_knowledge.py --strict` fails on any hit and on a missing terms file.

Provenance lives in the team vault, readable by every teammate's agent: `Runs/amazon-knowledge-ledger.md` (`type: reference`) holds one row per source thread with the unit id, client slug, channel, parent timestamp, permalink, dates, who diagnosed and executed, fix source, evidence location, identifiers and notes. Each sweep session also leaves `Runs/YYYY-MM-DD-knowledge-sweep.md`. `tools/knowledge/ledger.py check` confirms every unit has a row and every row a unit. Sweep working files (thread store, cards, review queue, staged ledger rows) stay in the gitignored `_local/knowledge-sweep/` and never enter the repo or the vault.

## Tooling

All retrieval and lint code is stdlib Python, because Grimoire runs on the PATH `python3` without PyYAML. Browser capture is Node and attended only.

| Command | Purpose |
|---|---|
| `python3 tools/search_amazon_libraries.py "<question>" --library kb --limit 5` | search units first (alias `knowledge`); `--library all` ranks them with the captures |
| `python3 tools/knowledge/new_unit.py --from-card <card.json>` or `--title ... --topic ...` | create a unit from a sweep card with the next id and a staged ledger row |
| `python3 tools/knowledge/build_knowledge_index.py --readme` | regenerate the index and README; `--check` fails on drift |
| `python3 tools/knowledge/lint_knowledge.py [--strict]` | format, enums, paths, scrub; run by `tools/lint_agent_docs.py` as check 10 |
| `python3 tools/knowledge/ledger.py check` | cross-check the vault ledger and the index; `append --from-staging` moves staged rows in (attended) |
| `python3 tools/knowledge/kb_status.py` | units past `review_by`, draft units older than 30 days, units citing changed pages |
| `python3 tools/knowledge/seed_redaction_terms.py` | rebuild the denylist from the vault and the Grimoire config |

Cards are the intermediate record between a source thread and a unit: `tools/knowledge/card.schema.json` defines them and `tools/knowledge/prompts/extract-card.md` tells an extraction agent how to fill one. A card keeps the identifiers; the unit never does.

## Cadence

Monthly: sweep the previous month's Slack threads, card them, review one batch. Quarterly: diff the help captures and check MAG SOP revisions, then re-verify the units `kb_status.py` lists. Any attended session that answered an Amazon question a teammate could ask again runs `/kb-add` before closing.
